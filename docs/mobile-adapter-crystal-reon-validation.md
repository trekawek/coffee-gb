This record covers the Phase 3 scenario in issues
[#353](https://github.com/trekawek/coffee-gb/issues/353) and
[#399](https://github.com/trekawek/coffee-gb/issues/399). The Coffee GB acceptance run uses
[`97fc57b4`](https://github.com/trekawek/coffee-gb/tree/97fc57b4e1c88923c8c479a49d9bbc9763e284c6),
which includes the adapter-image import, guest-write persistence, transfer timing, completion
cadence, history fencing, and bounded exact-alias prerequisites. The custom-service observation pins
[`REONTeam/reon@f7bfc0470aed561936b396ed29f2bde50ca601ab`](https://github.com/REONTeam/reon/tree/f7bfc0470aed561936b396ed29f2bde50ca601ab),
licensed MIT.

The adapter-image format provenance is narrower: REON's pinned MIT-licensed
[`web/htdocs/user/adapter_config.php`](https://github.com/REONTeam/reon/blob/f7bfc0470aed561936b396ed29f2bde50ca601ab/web/htdocs/user/adapter_config.php)
provides the public 512-byte producer, while pinned LGPL-3.0-or-later libmobile
[`config.c`](https://github.com/REONTeam/libmobile/blob/0704f56902f23b7ebf05c82c222e0e145e3140b6/config.c)
provides corroborating load/validation facts for the separate game-visible and library regions.
Coffee GB independently restates only the bounded format facts; no source text, data structure, or
control flow is copied.

Commercial-ROM evidence, the reproducible synthetic fixture, and the local REON run are kept
separate. No ROM, save, configuration image, account data, credential, checksum, proprietary packet
payload, screenshot, or captured server-response artifact is included. The requested declarative
hello document is reproduced below.

## Declared scenario and acceptance boundaries

| Layer | Declared input | Expected evidence | Result boundary |
|---|---|---|---|
| Real game | User-supplied Japanese Pokémon Crystal, synthetic adapter configuration, and no persistent battery write | Wake/poll `4b`; `10` BEGIN; `17` telephone status; valid request ACK, response packet, and response ACK | Confirms that the game recognizes the final link schedule and advances beyond the clean-master wait |
| Real utility | User-authorized Mobile Trainer and public demonstration registration values; clean, screen-driven first-run execution without a debugger override | Two changed configuration writes and their persistence; dial/login; exact-alias DNS; TCP/HTTP request, response delivery and drain, remote close, visible hello body, and cleanup | Passed through Coffee GB's production controller/backend path to the selected custom service. This complementary utility result does not substitute for Crystal networking |
| Deterministic integration | Synthetic configuration, raw-DNS fixture, TCP fixture mapped from guest port 8080 | `10`, `17`, `12`, `21`, `28`, `23`, repeated `15`, terminal empty `9f`, `22`, `13`, `11`; the declared 19-byte hello page and server EOF | Reproducibly covers the complete bounded endpoint/backend sequence, but is not ROM evidence |
| Custom service | Pinned REON checkout isolated on loopback with both runtime gates enabled | One exact route, HTTP reply, exact access count, and no ambient or wildcard DNS | Passed with one access entry for the expected route, status 200, and 19 response bytes; it does not claim Nintendo-service or general REON compatibility |

The strict end-to-end criterion is a request generated by the real utility and observed by REON,
followed by a response delivered to and drained through the utility's adapter session and verified
resource cleanup. The synthetic fixture and direct service preflight cannot satisfy that criterion by
themselves. Mobile Trainer visibly rendered `hello world`; no screenshot or private screen artifact
is retained or published.

## Reproducible committed evidence

The synthetic path is exercised without a ROM or external service:

```text
mvn -B -Dkotlin.compiler.daemon=false -pl controller -am \
  -Dtest=MobileAdapterCrystalWireIntegrationTest,MobileAdapterNetworkBackendTest,MobileAdapterDestinationPolicyTest,MobileAdapterConfigurationStoreTest,MobileAdapterControllerLifecycleTest \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

`MobileAdapterCrystalWireIntegrationTest` uses fixture-only names and payloads. It drives the
production endpoint and owner loop through the entire declared command sequence. Its TCP fixture
returns the declared 19-byte hello document with `Connection: close`; later TRANSFER commands drain
the response and consume server EOF as the required empty `9f` packet. Separate backend tests prove
that a response larger than one Mobile Adapter packet remains available to later transfers, that a
nonempty TCP write returns immediately when no reply is already available, and that an explicit
connection-ID-only receive poll may wait up to one second without releasing the logical slot.
`MobileAdapterDestinationPolicyTest` and `MobileAdapterConfigurationStoreTest` cover the bounded
exact-alias policy and its versioned persistence. `MobileAdapterControllerLifecycleTest` covers the
guest-write, completion-publication, history-fence, and teardown boundaries exercised by the manual
scenario.

## Real-game result

The clean-master baseline returned idle-high `ff` for every transfer. Crystal sent a valid BEGIN
request, received no acknowledgement or response, and did not issue telephone status.

With this Phase 3 endpoint, Crystal sent its leading `4b` wake/poll and completed these redacted
exchanges using one skipped `d2` turnaround transfer followed by one validated `4b`/`d2` response
gate:

```text
BEGIN             10 -> 90
END               11 -> 91
BEGIN             10 -> 90
TELEPHONE_STATUS  17 -> 97 (three-byte status)
END               11 -> 91
```

The game displayed its Mobile System adapter-check screen. This confirms ROM-level recognition of
the wake byte, request acknowledgements, skipped turnaround byte, validated `4b` response poll,
response stream, and response acknowledgement. It does not confirm later dialing or networking.

## Mobile Trainer hello-page acceptance

The separately authorized Mobile Trainer probe used Coffee GB's production controller, serial
endpoint, destination policy, network backend, and private configuration store. Rewind was disabled.
The owner-provided ROM was read in place and left untouched. A clean, screen-driven first-run replay
used only public demonstration registration values; no owner account or existing save entered the
run, and no debugger or guest-memory override was used.

The custom service used the pinned REON revision's DNS and nginx components on loopback. Guest DNS
was restricted to primary name `gameboy.datacenter.ne.jp` plus the one configured exact provider
alias `pop.aaa.dion.ne.jp`. Guest TCP port 80 was mapped to the loopback-only nginx listener, and
guest TCP port 110 was separately mapped to the loopback setup listener described below. No
wildcard record, ambient resolver, public destination, listener exposed beyond loopback, or
unconfigured port was available.

Following the public
[Mobile Trainer route](https://shonumi.github.io/articles/art14.html), the exact requested URL was:

```text
http://gameboy.datacenter.ne.jp/01/CGB-B9AJ/index.html
```

Its document was exactly 19 bytes, including the final line feed:

```html
<p>hello world</p>
```

The registration stage issued exactly two changed configuration writes. Each entered the bounded
guest-write persistence path with a correlated `pending` to `saved` transition, and the accepted
image remained authoritative while durability was pending; the final persisted image matched the
second accepted write. The setup's provider check issued one guest DNS query for configured exact
alias `pop.aaa.dion.ne.jp`, which maps to the policy's one primary target, and completed one bounded
TCP session. That loopback prerequisite is described separately below and is not counted as HTTP or
production-mail compatibility evidence.

After that deterministic first-run registration reached Mobile Trainer's title screen, one resident
interactive emulator session recorded this browser segment. A fresh screen-driven acceptance run
then replayed it without menu search or a restart between actions. Each button entry is
`button(held frames, dwell frames)`; `STEP` advances without a pressed button:

```text
A(3,180), SELECT(3,240), RIGHT(12,240), A(3,240), SELECT(3,240),
A(3,240), A(3,240), A(3,120), STEP(300), STEP(300)
```

The browser stage confirmed this sanitized, ordered lifecycle in the session's second network
connection:

```text
BEGIN -> TELEPHONE_STATUS -> DIAL -> ISP_LOGIN
DNS_QUERY -> TCP_OPEN -> five TRANSFER commands -> REMOTE_CLOSED
```

Every observed Mobile Adapter request and response checksum was valid. During the browser stage,
the utility issued exactly one DNS query for `gameboy.datacenter.ne.jp`, opened exactly one logical
TCP connection to the policy's guest-port-80 target, and sent this request line:

```http
GET /01/CGB-B9AJ/index.html HTTP/1.0
```

The request declared user-agent value `CGB-B9AJ-00`. The pinned REON nginx access output contained
exactly one entry for the route, with status 200 and 19 response bytes, and no access to another HTTP
route. The adapter trace recorded these packet-body lengths; the connection ID is included where
the command contract defines it:

| Browser transfer | Request length | Response result |
|---:|---:|---:|
| 1 | 5 | 1 byte |
| 2 | 24 | 1 byte |
| 3 | 39 | 1 byte |
| 4 | 1 | 251 bytes |
| 5 | 1 | `REMOTE_CLOSED` |

Coffee GB retained the response across the bounded transfers, delivered and drained it through the
utility's adapter session, and converted server EOF to the terminal remote-close result. Mobile
Trainer's browser visibly displayed `hello world`. At that point backend ownership was already
released and the endpoint parsers were clean while the guest remained on the browser page polling
telephone status. The replay also tried browser `B(3,240)` and observed only continued telephone-
status polling for the next 3,600 frames; page-history back with no prior page is therefore not
treated as a guest connection-teardown command. This result does not claim a subsequent guest
ISP-logout, hang-up, or END exchange. Controlled emulator shutdown then passed the harness's
aggregate cleanup check. This is owner-authorized Mobile Trainer evidence for the general custom-
server feature; it does not establish that Japanese Pokémon Crystal reached a network feature or
that arbitrary Mobile Adapter software is compatible.

## Loopback setup prerequisite

Mobile Trainer performs a provider check during first-run setup before its browser becomes
available. The acceptance harness supplied a loopback-only bootstrap fixture built from the pinned
REON revision's POP parser, framing, state, and response handlers. The fixture accepted nonempty
public demonstration fields for that one setup exchange without retaining or logging their values.
Its sanitized command boundary was `USER`, `PASS`, `QUIT`, followed by connection teardown.

This fixture was only a prerequisite for reaching Mobile Trainer's browser. It did not use REON's
production mail service or user database and does not prove provider authentication, account
compatibility, production POP behavior, or general REON mail compatibility. The provider name was
admitted only as a configured exact guest DNS alias. Only the subsequent ROM-originated HTTP request
observed in the pinned REON nginx access output is custom-service acceptance evidence.

## Adapter-image workflow

At the acceptance revision, the desktop retained this configuration dialog but kept its controls
hidden. The desktop now exposes the dialog and its owner-selected import control at **Peripherals →
Configure Mobile Adapter…**. The importer accepts an exact opaque 256-byte game-visible image, or an
exact 512-byte REON/libmobile envelope only after its `MA`/`LM` magic and checksums plus the `LM`
version and address types pass validation. It imports bytes `0..255` and discards the whole library
region, including device, DNS, relay, token, and host metadata.

Every import attempt revokes active backend ownership and both runtime-only authorization gates,
including stale, malformed, conflicting-source, busy, unreadable, and storage-failing attempts. An
accepted image keeps Coffee GB's device ID and structured custom-server policy, then persists only
the copied or extracted 256 bytes through the existing owner-only atomic store. It grants no
network authority. The workflow is now manually accessible; the completed Mobile Trainer-to-REON
result above remains the acceptance evidence rather than UI exposure alone.

## Privacy, state, and cleanup boundaries

- All validation networking is explicit, bounded, and restricted to authorized loopback/private
  development mode.
- An owner-selected image may contain private dial or account material. Coffee GB reads it with a
  strict bound, off the EDT, as a stable regular file while refusing a symbolic link in the final
  path component. It rechecks available identity, exact size, and timestamps around the read;
  non-default providers must supply a file key, while the default Windows filesystem uses the
  remaining metadata checks because none is available. It does not chmod or modify the selected
  source, create a file-level copy of it, or include its path/bytes in diagnostics. The selected
  path exists only for the duration of the queued import operation and is not logged or persisted.
  Observed instances of the private store target, same-file aliases, and atomic
  transaction-artifact names fail as
  `IMPORT_SOURCE_CONFLICT` before persistence starts; a stable source entry is left unchanged. Only
  the copied or extracted 256 bytes enter the private record and later deterministic save states.
- Java 16 cannot portably perform a descriptor-bound type/identity query or a nonblocking
  regular-file open. A process able to rewrite the selected directory can still substitute an
  entry between checkpoints or a FIFO during the narrow open window; select input from a private
  directory not writable by an untrusted process. Non-default providers without a file key fail
  closed as `IMPORT_READ_FAILED`; on the Windows default-filesystem fallback, a same-size
  substitution that preserves timestamps cannot be distinguished.
- TCP close, ISP logout, hang-up, end/reset, peripheral replacement, state load, rewind, and
  controller shutdown cancel or release backend ownership as documented in the Mobile Adapter
  contract.
- Save states include the deterministic 256-byte private adapter configuration. A state captured
  during a partial ISP-login packet can also include bounded ID/password parser bytes. Such states
  must remain private or be explicitly redacted.
- Socket, resolver, task, backend generation, request ID, and runtime connection ownership are not
  resurrected from a save state.
- Backend ownership was already released and endpoint parsers were clean at the visible browser
  result; controlled emulator shutdown then passed the aggregate cleanup check.
  Probe-only REON containers, locally built images, volumes, private overrides, generated
  configuration, temporary execution state, and captured response artifacts are private disposable
  validation resources and are removed after validation. The owner ROM was read in place and left
  untouched throughout the run.

## Remaining verified gaps

The boot-only Crystal probe still cannot dial or enter an online game feature, so it issues no DNS,
TCP, or HTTP request. The earliest known server route requires a user-owned, progressed Japanese
Pokémon Crystal save after returning the Mystery Egg to Elm, followed by **Title menu → Mobile
Stadium**. That private gameplay state is not repository evidence and no path, name, hash, or
content is recorded here. Obtaining and driving that owner-controlled state remains the current
Crystal end-to-end blocker.

Mobile Trainer supplies the shorter public HTTP route used above. Its clean first-run path no longer
depends on the debugger-assisted setup-state experiment from issue #448. The exact request/response
and controlled-shutdown cleanup demonstrate one complete owner-authorized
utility-to-custom-service flow. They do not expand the implemented packet subset or establish
compatibility with another title, provider, production account system, or service.

The custom-server policy admits one primary and at most seven additional exact guest DNS aliases
for the same configured target. This covers a bounded service family without multiplying port
mapping rules or allowing wildcard or ambient DNS access. Japanese Pokémon Crystal still needs a
user-owned progressed gameplay state and a fresh ROM-to-service trace before this document can claim
Crystal networking support; its present evidence remains adapter recognition only.
